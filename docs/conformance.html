Interpretations

The Recommendation leaves these points open, or reads two ways. Each entry gives the choice and the reason.

  1. When the state machine runs. It runs for every local event and for every R-APS that passes the validity check and the guard timer and outranks the persistent local requests. A persistent local request (latched FS/MS, SF, WTR/WTB running) that outranks a received R-APS, and has already been signalled, does not re-run its row. Re-running row 19 on every received R-APS(SF) would turn a stable (SF) into (SF,DNF), which contradicts Appendix III. The R-APS is counted as rx_suppressed.
  2. Command latches. FS/MS are latched while the node is in state D/C and are forgotten when it leaves (§10.1.9). An MS that would hit a no-action row (23/37/51) is rejected with a notification rather than latched.
  3. Re-evaluation. Persistent requests are re-evaluated after every state change. For example, an SF ignored in state D becomes the top request after Clear (row 44 → row 61).
  4. Dual SF. Two failed ports are one "failed ring port" set.
  5. BPR. BPR is the port the row is about if that port is blocked; otherwise the single blocked port; otherwise 0.
  6. Tx Version follows compatible_version: 0x00 for 1, 0x01 for 2. tx_version overrides it.
    • §10.3 says this edition transmits 0x01. The compatibility MI exists so that 2008-only nodes, which send and expect version 0, can share the ring. Set tx_version = 1 to follow §10.3 literally.
  7. Receive leniency. Any Version is accepted, Flags and the reserved fields are ignored, and TLV offset ≥ 32 is accepted. An End TLV is not required: only the 32 octets of R-APS information are read. This keeps forward-compatibility, as G.8013 asks of receivers.
  8. Clear at the RPL owner is rejected in states C/D without a local command.
    • These states exist only while an MS/FS is in effect. Otherwise a periodic R-APS(SF) on no-op row 49 would make Clear "valid", row 44 would leave the owner Pending without WTB, and the ring would never revert.
    • The chaos test found this.
  9. Software R-APS forwarding forwards like a hardware R-APS_FF: independently of the local validity check, subject to MEG-level filtering (MEL ≥ ring MEL) and to channel blocking. Own frames are never forwarded.
  10. Fail-safe dataplane. New R-APS information is not transmitted until the platform confirms every block the state machine asked for. A failed block is retried every 100 ms. Advertising (NR,RB) or (SF) while the block is not in place could let a peer unblock and close a loop.
  11. FOP-TO is off by default.
    • With an RPL neighbour configured, the owner's (NR,RB) is stopped at both RPL ends, so in Idle the ports facing the RPL legitimately receive nothing.
    • §10.4 excludes "when both ends are RB", but the detailed rule is in G.8021.
    • When enabled, FOP-TO is suppressed for SF ports and for the RPL port of the owner/neighbour in Idle.
  12. Restart (row 1) stops the guard timer, per the table. A node must therefore stay down longer than the ring's R-APS propagation time before restarting, as any real reboot does. The simulator and chaos test model this.
  13. Row 71 applies to every node in Pending, including the RPL owner and neighbour. The table gives row 71 no role condition, unlike row 15, and Appendix III scenario C step E has the owner unblock on a higher node ID.
    • The node with the highest node ID therefore keeps the only block. A second independent review proposed restricting row 71 to non-RPL nodes. That would keep the owner's RPL block and the highest node's block, which segments the ring. The literal row is kept and pinned by tests/scenario/test_review.c.
  14. Cold start. Row 1 starts WTR at a revertive owner.
    • On a ring powered up together, the owner's RPL block plus the init block of the highest-ID node can split the ring for the whole WTR (5 min by default). This happens when that node is not the owner.
    • init_wtb (CLI init-timer wtb) starts WTB instead, as in Appendix VIII Table VIII.1 row 1, so convergence takes guard + 5 s. It is off by default, to stay with normative Table 10-2.
    • A single node rebooting in a running ring is unaffected.
  15. Clear at the owner in Idle or Protection is accepted and runs no-action rows 2 / 16. Those rows exist for exactly this input (§10.1.9 b).

Known limitations

  • Sub-rings and interconnection (§9.7, §10.1.11, §10.1.12, sub-ring R-APS block logic) are not implemented.
  • Appendix VIII flush optimisation is not implemented (non-normative); only its row 1 start-up timer is offered, as init_wtb.
  • FOP-TO approximates G.8021's dFOP-TO (see interpretation 11).
  • Performance (§7.3, < 50 ms) depends on the platform's SF detection, CPU trap latency and timer resolution. The library's processing is synchronous and O(1) per input.
